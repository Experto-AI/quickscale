# Changelog

`CHANGELOG.md` is the canonical QuickScale release history index. Published releases pair each version entry with a single official release note in `docs/releases/` linked from the GitHub tag and release PR. When a release note is prepared before the maintainer completes the manual tag/publish step, the changelog entry and note must say so explicitly and must not imply publication. Use `docs/technical/roadmap.md` for active or unpublished release status. Entries are version-ordered.

    - 2026-06-27 — **AF5: Apply step executor with per-step checkpoint/resume, destructive confirmation gate, and fault-injection harness (Track 3).** Each apply step now carries an `is_satisfied()`/`apply()` contract via `ApplyStepProtocol`. After each non-destructive step (1–10), `ApplyExecutor.checkpoint_step()` writes a `ResumeCheckpoint` to the `RecoveryLedger` (`.quickscale/apply-recovery.yml`). On rerun after a mid-pipeline failure, `ApplyExecutor.find_first_unsatisfied_step()` reads the checkpoint and resumes from the first incomplete step. Backward-compatible with AF6-era ledgers that lack the `resume_checkpoint` field (treated as `None`, triggering a full rerun). Steps 11–16 (mutable config, Docker startup, database migrations, Railway deploy, state finalization, next-steps display) are grouped into a separately-confirmable destructive/remote phase with an explicit operator prompt. A deterministic fault-injection test harness (AF5 Phase 3) kills after step N, verifies ledger checkpoint correctness, then reruns and asserts convergence across all 16 steps. Phase 1: `ResumeCheckpoint` + `RecoveryLedger` schema. Phase 2: executor-driven resume in `_execute_apply_steps_locked`. Phase 3: fault-injection test harness. Phase 4: destructive/remote confirmation gate.
