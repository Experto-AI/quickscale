## Autopsy — 2026-07-02

### Orientation

A creator-led (solo maintainer, 1,381 commits, weekly cadence, tags through 0.86.0) **monorepo of three archetypes**: a CLI (`quickscale_cli`, Click), a generator/engine library (`quickscale_core`: Jinja2 scaffolding, plan/apply state machine, manifest stack, DR engine), and ~13 first-party Django modules (`quickscale_modules/*`) distributed into generated projects as user-owned git subtrees. Generated apps: Django 6 + PostgreSQL 18, single Railway deployment, multi-tenant via FORCE RLS + `TenantManager` (v0.86.0 architecture, hardened by the 2026-06-30 autopsy remediation). Tool-side state: `quickscale.yml` (desired) / `.quickscale/state.yml` (applied), advisory-locked apply with a saga-style recovery ledger. **Growth direction:** teams module (placeholder today; design locked in `docs/technical/organizations.md`), more org-scoped tenant tables (Option C: every child table carries `organization_id`), vertical themes planned. **Stated-vs-actual gaps noted:** `decisions.md:1145` references `findings.md §Finding-8` and `roadmap.md §AF8`, which no longer exist; the Module Implementation Checklist still describes `AVAILABLE_MODULES` as a hand-edited list though it is now discovery-derived (`module_commands.py:65`). **Depth:** read fully — the module-wiring seam (CLI `module_config.py`/`apply_command.py`, core `contracts/*`, `manifest/entry_point.py`), the tenancy seam (`orgs` tenancy/managers/middleware/checks), module manifests, decisions.md; sampled — DR engine, theme templates, generated-project templates, apply ledger; skipped — module domain logic internals, devtools, htmlcov/examples. Roadmap is empty ("no open items"), so urgency judgments below are calibrated to the teams/SaaS direction, not to scheduled work.

Severity floor: the CLI/generator is a single-process local tool (concurrency lenses discounted); generated apps are single-service WSGI (distributed-systems lenses discounted); tenant isolation is the highest-blast property in the system.

### Finding 1: Per-module integration knowledge is fanned across three packages, with two wiring mechanisms coexisting and the declared migration unscheduled

- **Rank rationale (blast radius × likelihood):** Every module addition and every module-option change pays a 5–9 file coordination tax across `quickscale_cli` + `quickscale_core` + the module — likelihood ≈ 1 (it is the product's main axis of growth), blast = the three highest-churn files in the repo.
- **Horizon:** now — this is the tax on all current work; the teams module will pay it in full.
- **Confidence:** High. Verified directly by symbol listings of all files cited; the two-mechanism state is documented in `decisions.md` itself.
- **Context dependence:** wrong-regardless — for a product whose unit of growth is "add a module," per-module knowledge belongs in the module.
- **Problem:** Module wiring is a platform-side, hand-coded concern: each module's defaults, normalization, validation, derivation schema, CLI prompts, apply hooks, and env-example rendering are separate hand-written functions in central files, while the declared replacement (manifest-driven derivation, piloted on analytics in SA5.1) covers 1 of 12 modules and its continuation is on no roadmap.
- **Evidence:**
  - `quickscale_core/src/quickscale_core/contracts/resolvers.py` (1,781 lines) — per-module quintuples `default_/normalize_/resolve_/validate_*` plus hand-built `_build_<module>_derivation_schema()` for all 12 modules (e.g. notifications' schema alone is `resolvers.py:894–1104`).
  - `quickscale_core/src/quickscale_core/contracts/module_options.py` (1,036 lines) — per-module option constants.
  - `quickscale_cli/src/quickscale_cli/commands/module_config.py` (2,098 lines) — per-module `get_default_/configure_/apply_<module>_configuration` triads (auth :283, blog :587, listings :660, crm :718, forms :832, storage :934, backups :1260, notifications :1444, analytics :1618, billing :1745, social :1855, orgs :1974).
  - `quickscale_cli/src/quickscale_cli/commands/apply_command.py:1134–1509` — module-specific logic inside the apply orchestrator: `_render_notifications_env_example_block`, `_sync_analytics_env_example`, `_render_billing_env_example_block`, `_ensure_backups_gitignore_rules`.
  - `quickscale_core/src/quickscale_core/manifest/entry_point.py` (1,460 lines) — split mechanism: core-inline adapters for analytics/blog/listings/forms/backups/notifications/auth (`MANIFEST_ADAPTER_REGISTRY` assignments at :351, :423, :482, :553, :690, :952, …) vs module-owned managed adapters only for billing/crm/social (`MANAGED_ADAPTER_ORIGINS` :360, :491). `manifest/social_manifest.py` (514 lines) is an entire module-specific renderer file living in core.
  - Migration state: `contracts/imperative_inventory.py:64` — `ANALYTICS_MANIFEST = []` (fully migrated) while all other modules hold populated freeze lists; `decisions.md:715` — "Later phases will add loader wiring, runtime derivation execution, and progressive contract-file deletion — one module at a time"; `roadmap.md:50` — "No open items."
- **Why it compounds:** Adding one module today means coordinated edits to `module.yml`, `module_options.py`, `resolvers.py` (≈5 functions), `entry_point.py` (adapter or origin registration), `module_config.py` (3 functions), possibly `apply_command.py` (env-example/gitignore hooks), `imperative_inventory.py`, plus theme templates and docs — the checklist in `decisions.md:816–831` institutionalizes this as process. Meanwhile every new option lands on whichever of the two mechanisms its module happens to be on, deepening the split the longer it persists. Two mechanisms also means every engine improvement (validation errors, drift detection) must be built twice or diverge.
- **Correct shape:** All knowledge specific to module X lives in module X's package (manifest + module-owned adapter); central code contains only the generic engine — the invariant is "adding a module touches zero central files that enumerate modules."
- **Trigger for urgency:** The teams module — the next planned module — will either be built on the legacy path (adding a 12th imperative wiring set under a freeze meant to prevent exactly that) or force the derivation engine to be finished under feature pressure.
- **Compounding factor:** All 11 unmigrated modules, the freeze inventory (which must shrink module-by-module as the migration proceeds), and the SA5.2 guardrail test (`quickscale_core/tests/test_imperative_inventory.py`) which codifies today's split as the frozen baseline.
- **Detection signal:** In git history, any module-option PR touching ≥4 central files (already observable across the v0.8x series). Instrument: track "files changed per module-scoped PR" — it should trend toward 1–2.
- **Strongest counter-argument (steelman):** This is a known, deliberately staged migration: the pilot shipped, the freeze prevents regression, and a solo maintainer amortizes migration cost against feature work rationally. That holds *if* the migration is actually scheduled — but the roadmap is empty and the next module will arrive before the engine does. Choose not to fix only if no new modules or options are expected for several releases.
- **Alternative solutions:**
  1. **Finish the declared derivation migration, landing adapters module-side** — extend `module.yml` with the deferred `derivation:` section + YAML loader, migrate one module per release via the existing `MANAGED_ADAPTER_ORIGINS` mechanism, deleting its `resolvers.py`/`module_config.py`/`entry_point.py` code as it moves. Effort: medium per module, spread; reversible per module; removes ~all of the tax.
  2. **Consolidate without migrating** — keep imperative wiring but collapse each module's scattered functions into one `contracts/modules/<name>.py` implementing a small protocol. Effort: low; bounds fan-out to one central file per module but keeps knowledge platform-side and keeps two mechanisms.
  3. **Freeze the surface** — declare the current 12 modules the permanent set and accept the tax for options only. Effort: zero; contradicts the teams roadmap, so not credible.
- **Preferred option + why:** (1) — it is the architecture the project already chose and partially built; the managed-adapter vehicle exists and is proven on billing/crm/social; the freeze guardrail was explicitly designed to hold the line while it happens. (2) is a fallback if YAML derivation proves too rigid for gnarly modules (notifications, backups).
- **Migration path:** Put the next derivation slice on the roadmap now — ship the `module.yml` `derivation:` loader and migrate one small module (listings or blog) end-to-end, deleting its imperative entries from the freeze inventory.

### Finding 2: `orgs` is becoming the composition god module — inter-module integration is hand-wired pairwise with no contract, and the central tenant registry couples all module versions in lockstep

- **Rank rationale:** Every new tenant model in *any* module requires editing the orgs module and its docs assertion; the module workspace's core promise (independently versioned, subtree-updatable modules) is silently voided — likelihood ≈ 1 with the teams module and Option C ("every future table"), blast = the tenant-isolation surface plus the distribution model.
- **Horizon:** now — the coordination cost is already being paid; the skew risk activates the first time a user updates modules selectively.
- **Confidence:** High for the coupling mechanism (verified in code); Medium for the skew severity (depends on how users actually run `quickscale update`; runtime posture on mismatch is warn-only, verified in `checks.py`, with CI as the fail-closed layer).
- **Context dependence:** wrong-for-now — dimension: module count and the independent-release promise. With 3 modules and lockstep releases it would be fine; with 13 independently versioned modules plus subtree distribution it is not.
- **Problem:** The foundation module owns per-module knowledge about every leaf module — tenant-table enrollment, purge ordering, CRM bootstrap, auth adapter subclassing, even notifications' full default config — so dependency arrows point both ways and there is no defined seam by which modules compose; four different ad-hoc idioms substitute for one.
- **Evidence:**
  - `quickscale_modules/orgs/src/quickscale_modules_orgs/tenancy.py:119–350` — `TENANT_TABLE_REGISTRY` centrally enumerates 21 models belonging to CRM, Forms, Billing, Blog, Listings, and Social by `app_label`/`model_name` string.
  - `orgs/.../management/commands/purge_organization.py:67–543` — hand-maintained per-module app-label deletion ordering plus a guarded deferred import of `quickscale_modules_social.contracts`.
  - `orgs/.../crm_bootstrap.py:14–26` — orgs seeds CRM default stages via `apps.is_installed(...)` + `import_module(...)` (idiom 2).
  - `orgs/.../adapters.py:19–24` — `try: from quickscale_modules_auth.adapters import ... except ImportError: fallback to DefaultAccountAdapter` (idiom 3 — and a silent-fallback import in a setup path, in tension with `decisions.md` §fail-hard-principle which prohibits exactly this).
  - `quickscale_modules/orgs/module.yml` `implies:` — orgs embeds notifications' complete `default_config` (sender, tags, TTL) inline, duplicating another module's defaults (idiom 4).
  - Version coupling with no contract: `quickscale_modules/crm/module.yml` `required_modules: [orgs]` carries **no version constraint**, while module versions already diverge (crm 0.73.0, billing 0.85.0, orgs 0.86.0). A crm subtree update that adds a model needs a matching orgs update to stay classified; nothing expresses or checks that.
  - Enforcement posture: `orgs/.../checks.py:1–15` — the SA1.4 default-deny classification check is **WARNING-level at boot** ("do not block startup"); the fail-closed layer is the CI management command. Plus the count assertion embedded in a doc comment, `decisions.md:1180`.
- **Why it compounds:** Under Option C every future tenant-owned table in every module adds a registry entry, a purge-order position, and a doc-count bump inside orgs — O(models × modules) edits concentrated in the one module that everything else depends on. Each new cross-module behavior (teams↔billing, teams↔notifications) has no seam to land on, so it will be hand-wired as a fifth idiom, further entangling orgs.
- **Correct shape:** Modules declare their own tenant surface and org-lifecycle participation (in their package: manifest section or model marker); orgs owns *enforcement and audit* — default-deny over discovered declarations, conformance gates, purge execution derived from FK topology — but never authors per-leaf knowledge. Invariant: "a module can add a tenant model without editing any other module."
- **Trigger for urgency:** Teams module implementation (new tenant tables + memberships interacting with billing and notifications), or the first bug report from a generated project whose module subtrees were updated out of lockstep.
- **Compounding factor:** The 21 enrolled models, the SA1.3/SA1.4/SA1.5 conformance gates (their *checks* are right and should survive any fix; their *fixture* — the authored registry — is the coupling point), `purge_organization`, and the doc-consistency gate asserting the counts.
- **Detection signal:** Git history already shows it: model changes in blog/crm ship paired with `orgs/tenancy.py` edits (SA1.1/SA1.2 commits). Watch for `quickscale_modules_orgs.W00x` classification warnings in generated-project logs — each one is a skew event the runtime tolerated.
- **Strongest counter-argument (steelman):** The central registry was built deliberately *last week* (SA1.4) as a single audit surface for the most security-critical invariant in the system, and a single human-reviewable list of every tenant table has real security value. This holds for the *audit* function — but auditability survives if the registry is derived-at-boot from module-owned declarations and snapshot-tested centrally; it does not require central authorship. Choose not to fix if modules abandon independent versioning and formally adopt lockstep releases (that would also need `required_modules` version pins to say so).
- **Alternative solutions:**
  1. **Module-owned declarations, derived registry** — each module declares tenant tables in its own package (its `module.yml` or model-level marker; `TenantModel` subclassing already exists as the mechanical marker); orgs builds the registry at app-ready from declarations, keeps default-deny for anything undeclared, and a central snapshot test preserves the audit surface. Purge ordering derived from Django's FK collector. Effort: medium; removes the O(models) cross-module edits; keeps every gate.
  2. **Keep central authorship, add version discipline** — `required_modules` gains version ranges; `quickscale apply`/`update` fail when installed module versions are outside the orgs registry's supported range. Effort: low; makes lockstep explicit and safe but keeps the coordination tax.
  3. **Composition contract for behavior** — define the documented extension seam (Django signals or a small hook registry within the existing extension contract) for org lifecycle events; crm_bootstrap becomes a CRM-side `org_created` receiver, purge becomes modules contributing their own deletion plans. Effort: low-medium; fixes the reverse dependencies but not the registry.
- **Preferred option + why:** (3) first, then (1). The reverse-dependency idioms (crm_bootstrap, auth adapter fallback, notifications defaults in orgs' manifest) are cheap to invert and stop the god-module accretion immediately; the registry inversion is worth doing calmly before teams lands, preserving the just-built gates as the enforcement layer. (2) is the stopgap if teams must ship first.
- **Migration path:** Convert `crm_bootstrap.maybe_seed_crm_default_stages` into a CRM-side receiver of an `organization_created` signal exposed by orgs — one seam, one PR, establishes the pattern.

### Finding 3: "Active organization" has two sources of truth in generated SaaS apps — the server session and the SPA's client state — and the shipped resolution was to amputate features (D1 Option B)

- **Rank rationale:** Cross-org data exposure in a paying-tenant context is near-maximal blast; the trigger has already fired once (billing UI removed rather than risk wrong-org reads), and the teams UI re-arms it — likelihood high within the stated growth direction.
- **Horizon:** now — the seam is "resolved" only by feature absence; the moment any org-scoped SPA surface ships (teams, restored billing cards), the same collision returns.
- **Confidence:** High. The mechanism is documented as a locked decision (`decisions.md:320–331`) and verified in code; the wrong-org read itself needs a running app to demonstrate (static-analysis caveat — confirm by switching orgs in the SPA and inspecting which org a subsequent session-scoped API call resolves).
- **Context dependence:** wrong-regardless — a dual source of truth for the tenancy selector is wrong in any multi-tenant app; severity scales with the SaaS direction.
- **Problem:** Ambient server-side org resolution (session key → middleware → ContextVar → RLS GUC) and client-side org switching in the generated React SPA are two independent authorities for the same state, with no sync contract — so any SPA surface that relies on ambient scoping can silently operate on the previous org after a client-side switch.
- **Evidence:**
  - `decisions.md:320–331` — "D1 … the server session `ACTIVE_ORG_SESSION_KEY` is not explicitly synced before billing API calls fire. This means billing pages can resolve the wrong org after a client-side switch. QuickScale has locked **Option B** — remove generated SPA billing entry points … Option A (session-sync endpoint) is deferred."
  - Server authority: `quickscale_modules/orgs/src/quickscale_modules_orgs/views.py:565` (`request.session[ACTIVE_ORG_SESSION_KEY] = str(organization.pk)`); `middleware.py:122–139` (`_handle_saas_request` resolves org from the session, popping it when invalid); `current_org.py:163–181` (ContextVar + `SET LOCAL app.current_org_id` — the RLS enforcement input).
  - Client authority: theme hook `showcase_react/src/hooks/useOrgs.ts.j2:99–107` builds slug-scoped API paths (`/api/orgs/${orgSlug}/…`, `/orgs/${orgSlug}/api/billing/…`) from client-held state, independent of the session.
- **Why it compounds:** Every module that ships an org-scoped React surface must individually solve or dodge the sync problem; the shipped precedent is "dodge" (remove the surface), which is a per-module recurring amputation. Meanwhile the flat-route + ambient-session architecture is a locked permanent rule (`decisions.md:1227`), so the class of session-scoped APIs keeps growing.
- **Correct shape:** Exactly one authority for active org per request class, enforced by contract: org-scoped API requests carry the org explicitly and the server validates membership (session never consulted), while ambient session scoping is reserved for server-rendered flat routes; any client-side switch that must affect ambient state goes through an awaited sync endpoint before dependent queries fire.
- **Trigger for urgency:** Teams module UI (org switching is its core interaction), or restoring the billing SPA entry points (explicitly gated on solving this — `decisions.md:198–199`).
- **Compounding factor:** The removed billing dashboard cards/nav/`modulePaths.billing` (must be re-added once fixed), `useOrgNavigation`/`useOrgs` hooks, and every future org-scoped SPA page. RLS makes the failure *safe* (no cross-org leak — queries scope to the session's org) but *wrong* (user sees org A while acting on org B), which is a billing-grade correctness bug.
- **Detection signal:** Nothing observable today precisely because the surface was amputated — the signal *is* the amputation pattern recurring. When org-scoped SPA surfaces ship, instrument: server logs comparing the org implied by the request's slug/body against `request.session[ACTIVE_ORG_SESSION_KEY]`; any mismatch is the bug firing.
- **Strongest counter-argument (steelman):** Option B was a disciplined, explicit scope cut — no user-visible wrong-org behavior shipped, and the decision record says it will be revisited with a designed contract. That is true and creditable; the finding stands because the *decision to design the contract* has no roadmap slot while the feature that needs it (teams) is next. Don't fix only if generated SPAs will never ship org-scoped pages — contradicted by the org-switcher already being a stated architecture element (`decisions.md:1167`).
- **Alternative solutions:**
  1. **Explicit-org API contract** — all org-scoped JSON APIs take the org slug in the path (already the pattern in `useOrgs.ts` and permitted by `decisions.md:1227` for `/api/orgs/<slug>/`); server validates membership per request; session scoping retained only for server-rendered routes. Effort: medium; removes the dual authority for the entire API class; no sync step to forget.
  2. **Option A session-sync endpoint** — SPA POSTs the org switch and awaits 200 before firing org-scoped queries; TanStack Query invalidation keyed on active org. Effort: low-medium; keeps ambient scoping but reintroduces a per-callsite discipline ("await the sync") that degrades exactly like procedural tenant filtering.
  3. **Server-driven switching** — org switch is a full navigation through the existing switch view (redirect), so client state never diverges. Effort: low; costs SPA fluidity; fine as a stopgap.
- **Preferred option + why:** (1). It makes the org an explicit, validated request parameter — structural, not procedural — and matches the slug-scoped org-admin API surface already shipped; (2) is acceptable only as the documented bridge for surfaces that must stay session-ambient.
- **Migration path:** Write the D1 Option A/explicit-org contract decision now (before teams UI), starting with a membership-validating request wrapper in the theme's `useApi` that requires an org argument for org-scoped endpoints.

### Finding 4: `quickscale_core`'s entire internal surface is a de facto runtime API for user-owned generated projects — with an open-ended version range and a repo-wide clean-break policy

- **Rank rationale:** A core refactor can break deployed, user-owned projects at `poetry update` or fresh install; likelihood is low today (no external users) but flips to certain-eventually as adoption grows, and the surface is enlarging (the F5 DR extraction moved *more* code into core).
- **Horizon:** 6–18 months — the first external adopters make this permanent; the cost of drawing the boundary grows with every release that widens the reachable surface.
- **Confidence:** High for the mechanism (imports, dependency declaration, and policy all verified); severity Medium (depends on adoption timing).
- **Context dependence:** wrong-for-now — dimension: external users. As a private toolkit this is harmless; as a published PyPI product ("Install from PyPI (Recommended)", README) it is a latent contract break.
- **Problem:** Embedded modules — which become user-owned code in generated projects — import deep internals of the generator package (`dr_engine.orchestration`, `contracts.resolvers`, `manifest.assembler`), and the generated project depends on `quickscale-core>=0.86.0` with no upper bound, while the project's stated versioning philosophy is "no back-compat, every change is a clean break" — three commitments that cannot all hold once a project exists in the wild.
- **Evidence:**
  - `quickscale_modules/backups/module.yml` — `dependencies: … quickscale-core>=0.86.0` (flows into the generated project's `pyproject.toml` via dependency sync).
  - `quickscale_modules/backups/src/quickscale_modules_backups/services.py:18,72,103,119` — runtime imports of `quickscale_core.dr_engine.{orchestration,primitives,recovery,verification}`; seven management commands import `dr_engine.adapter.ADAPTER_FUNCTIONS`.
  - `quickscale_modules/social/src/quickscale_modules_social/adapter.py:18–33` — module-owned code importing `quickscale_core.contracts.{module_options,resolvers}` and `manifest.{assembler,resolver,social_manifest}` (apply-time, but it lives in the user-owned subtree).
  - Policy: `decisions.md:1137` — "No existing users, no migration path, no backward compatibility — every change is a clean break."
  - No boundary exists: `core-compatibility` metadata appears only as an aspirational example (`decisions.md:1291–1295`); grep confirms it is implemented nowhere; no `__all__`-style public facade, no import-linter contract, no semver policy in `versioning.md`/`release_policy.md`.
- **Why it compounds:** Each engine-ification (DR was the first; derivation execution per Finding 1 is next) moves more logic into core that modules then import — the reachable surface grows monotonically, and every symbol it exposes today is a symbol some generated project may reference tomorrow. Once N projects exist, every core refactor costs O(N) potential breakage or forces the back-compat layer the project's philosophy forbids.
- **Correct shape:** A named, versioned public surface (facade module or separate `quickscale-runtime` distribution) that is the *only* thing module code and generated projects may import, with a compatibility policy for it — clean breaks stay legal for everything behind it. Invariant: "no user-owned file imports a core symbol the maintainer hasn't promised to keep."
- **Trigger for urgency:** First external adopters running `poetry update` across a core minor release; or the Finding-1 derivation migration, which will otherwise mint a second module→core runtime dependency pattern.
- **Compounding factor:** The DR engine split (F5.2–F5.4) and its adapter, the backups module's seven management commands, `social/adapter.py`, and the managed-adapter mechanism (module-owned adapters import `manifest.*` by design).
- **Detection signal:** None today (no external users — this is the static-analysis-caveat finding). Instrument now: a CI job that installs each module against the *oldest* core version its `module.yml` claims (`>=0.86.0`) and imports it; the day that job needs an upper bound, the contract gap is live.
- **Strongest counter-argument (steelman):** One maintainer controls both sides and releases them together from one repo; "no existing users" is currently true, and pinning too early adds friction to a fast-moving 0.x line. Legitimate today — but the README actively recruits PyPI users, and the fix costs one line per module manifest now versus a compatibility program later. Don't fix only if QuickScale is retired from public distribution.
- **Alternative solutions:**
  1. **Compatible-range pinning at embed time** — dependency sync writes `quickscale-core>=X.Y,<X.Y+1` (the core version paired with the embedded module); `quickscale update` moves the pin with the subtree. Effort: trivial; kills the skew hazard; defines no boundary.
  2. **Public runtime facade + import gate** — `quickscale_core.runtime` (re-exporting the DR adapter and whatever derivation runtime needs) as the only legal import for module code, enforced by a CI import-linter check over `quickscale_modules/*/src`; semver honored for the facade alone. Effort: low-medium; makes the clean-break policy safe forever.
  3. **Vendor the runtime into generated projects** — subtree/vendor the needed engine code like modules themselves, so generated projects have zero dependency on the tool's PyPI package. Effort: high; maximally aligned with "user owns everything," but forks the engine per project and bloats updates.
- **Preferred option + why:** (1) immediately, (2) before the derivation runtime (Finding 1) ships — that migration will otherwise hard-wire a second internal surface into every module. (3) only if the product later promises tool-free generated projects.
- **Migration path:** Change `backups/module.yml` to a compatible-range pin and add the module-vs-oldest-core import job to CI — one PR, closes the live hazard, and forces the facade conversation when it first fails.

### Finding 5: The module↔generated-project contract drifts by design — every release accretes "existing projects must manually adopt" steps with no mechanism to apply them

- **Rank rationale:** Cost is per-project × per-release and lands on users (or on the maintainer's own older client projects); blast is currently small but strictly monotonic with the installed base.
- **Horizon:** 6–18 months — grows with each generated project that lives long enough to cross a module-contract change.
- **Confidence:** Medium — the pattern is thoroughly documented and structural (verified in decisions.md and templates); the accumulated real-world pain is inferred, since the installed base today is the maintainer's own projects.
- **Context dependence:** wrong-for-now — dimension: installed base × release cadence. With three long-lived projects it's a chore; with fifty client projects it's the support burden.
- **Problem:** Modules keep evolving via subtree updates (runtime contract moves), but their integration points in generated projects — theme-owned pages, Docker/CI/E2E workflow files, frontend hooks — are one-time-copied and never revisited, so the system's own docs must repeatedly carve out "fresh generations only / manual adoption" exceptions, and each exception is a permanent fork in the supported-configuration matrix.
- **Evidence:**
  - `decisions.md:626–632` — "`quickscale apply` … does NOT rewrite user-owned Docker, Compose, CI, or E2E workflow files in already-generated projects; when the PostgreSQL 18 backups contract requires new image packages or runner tooling, existing generated projects MUST adopt those changes manually."
  - `decisions.md:296–301` — public `/social` pages exist only on fresh `showcase_react` generations; `decisions.md:318` — "newly scaffolded theme-owned routes, navigation, registries, and page source are only guaranteed on fresh generation or explicit manual adoption."
  - README.md:54 — same manual-adoption clause repeated user-facing.
  - The counter-mechanism exists but is scoped narrowly: managed wiring files (`quickscale_core/module_wiring.py:85–199` rendering `settings_modules.py`/`urls_modules.py`; `managed_files` hashes in `.quickscale/state.yml`) give apply a rewritable surface — but only for settings/urls wiring, not for the theme/infra files the exceptions keep accruing around.
- **Why it compounds:** Each release adds rows to an (generation vintage × module version) support matrix that nobody can test — the repo's own release notes and decisions.md are already spending paragraphs per release fencing it. Every future module frontend feature repeats the choice: fresh-only (fork the matrix) or rewrite user files (violate ownership).
- **Correct shape:** An explicit, versioned boundary between QuickScale-owned and user-owned files in generated projects, where everything QuickScale-owned is reachable by `apply` (the managed-files mechanism, broadened), and contract gaps are *detected* rather than documented — apply knows the project's contract vintage and says what's missing.
- **Trigger for urgency:** First cohort of external users' projects hitting a required manual adoption (the PostgreSQL 18 tooling change was the dry run); or vertical themes multiplying the theme-owned integration surface.
- **Compounding factor:** Every already-generated project; the D1 amputation (restoring billing UI to *existing* projects will be a manual-adoption note under today's rules); module flags files and env examples that are already quasi-managed.
- **Detection signal:** Count "manual adoption" clauses per release note (rising across v0.77–v0.86); support requests of the form "module update broke my project's CI." Instrument: have `quickscale status` report the project's generation vintage vs. current contract version.
- **Strongest counter-argument (steelman):** "Generated code is 100% user-owned, no vendor lock-in" is the product's core promise — auto-rewriting user files would betray it, and manual adoption is the honest price. This holds for genuinely user-customized code; it does not hold for files users never touch (CI workflows, module nav registries, env examples) where ownership is nominal and the manual step is pure toil. Don't fix if the installed base stays ≤ a handful of maintainer-controlled projects.
- **Alternative solutions:**
  1. **Broaden the managed-file surface** — classify generated files as managed vs user-owned at generation time (manifest-declared, hash-tracked like `managed_files`); apply rewrites managed files on module update, never user-owned ones. Effort: medium; removes most of the toil; needs a careful takeover story for files users *did* edit (hash mismatch ⇒ refuse and report, consistent with fail-hard).
  2. **`quickscale adopt` codemods** — per-release, opt-in patch scripts for existing projects. Effort: medium-high ongoing; preserves ownership absolutely; each codemod is write-once-run-everywhere but the catalog grows forever.
  3. **Contract-vintage detection only** — `module.yml` declares a required project-contract version; `apply`/`status` diff it against the project and print the exact manual steps. Effort: low; formalizes the status quo and makes the matrix visible, fixing detection but not toil.
- **Preferred option + why:** (3) now (cheap, honest, and makes the real cost measurable), graduating to (1) for the file classes that are QuickScale-owned in all but name — which is also the infrastructure D1's billing-UI restoration will want.
- **Migration path:** Add a `project_contract` version to state.yml and a `quickscale status` check that names any module whose embedded version postdates the project's generation vintage contract.

Same decision rules as the repo-level autopsy, applied per module in `quickscale_modules/`, in blast-radius order. Cross-module structural issues already reported above (wiring fan-out, orgs god-module coupling, core-as-runtime-API, D1 org sync) are **not repeated** here; this pass looks *inside* each module. ### Module Finding 1: The request→tenant-context boundary is a per-module convention with divergent idioms — and blog/listings public pages read as empty under the hardened production posture

- **Rank rationale (blast radius × likelihood):** The public content surface of every generated SaaS app (blog, listings) silently renders zero rows in exactly the configuration the SA2.x remediation made mandatory (restricted `NOBYPASSRLS` runtime role); likelihood ≈ 1 on first properly-hardened saas deploy. The root — five modules, five hand-rolled org/auth resolution idioms — degrades further with every new module surface.
- **Horizon:** now — this is a live defect in shipped module code, currently masked because dev and module tests run as superuser.
- **Confidence:** High (static). Every link in the chain verified in source; needs one runtime confirmation: deploy a saas-mode app under `RUNTIME_DATABASE_URL`, publish a System-org post, request `/blog/` logged out, observe an empty list.
- **Context dependence:** wrong-regardless — a per-callsite two-obligation contract (filter AND prime the GUC) around a security boundary is exactly the procedural-isolation shape the project's own decisions.md prohibits.
- **Problem:** There is no shared request-context layer for module HTTP surfaces. `TenantMiddleware` only establishes tenant context for authenticated requests, so every module invents its own resolution for the rest — and the D2 contract ("anonymous visitors see System-org rows") is implemented per-module, with blog and listings implementing it only at the queryset-filter level while the RLS layer (strict GUC equality, no System-org carve-out) hides every row because nothing primes the GUC for anonymous readers.
- **Evidence:**
  - The failure chain: `middleware.py:96–98` (unauthenticated → early return, no ContextVar); `current_org.py:476–479` (AF9 wrapper: "No org context — pass through without priming"); `tenancy.py:414–421` (policy: `USING (NULLIF(current_setting('app.current_org_id', true), '')::uuid = organization_id)` — no System-org exception); `blog/views.py:63–75` (`_resolve_org_for_read` returns the System org object but never calls `set_current_org_id`/`tenant_context`); `blog/views.py:772–779` (`Post.all_objects.filter(status="published")` + `.filter(organization=system_org)` — manager bypassed, RLS not satisfied); `listings/views.py:209–220` (same shape). Result: zero rows under the restricted role.
  - The correct idiom exists — in one module: core-rendered social public views wrap reads in `tenant_context(resolved_org_id)` (`quickscale_core/manifest/social_manifest.py:444–447, 471–474`), which primes the GUC and works under RLS.
  - Why no test catches it: module suites run as `postgres` superuser with `QUICKSCALE_ALLOW_BYPASSRLS=1` (`blog/tests/settings.py:10,66`; same in orgs) — superusers bypass RLS unconditionally, so the anonymous-read path under the production role is structurally untestable there. The SA1.3 conformance gate checks policy *existence*, not anonymous read behavior; the only restricted-role runtime tests are CRM's (`crm/tests/test_isolation.py`), and CRM has no public surface.
  - The idiom divergence (the root): blog `_resolve_org_for_read` (System-org, no priming) and `_resolve_api_org` (`blog/views.py:77–98` — token-auth writes fall back to the user's personal org *or the System org*, i.e. a failed lookup can target public content); crm `_resolve_active_org` (`crm/views.py:44–75` — primes correctly, but embeds a stage-seeding **write** on every resolution and a "for tests that bypass middleware" personal-org fallback living in production code); billing `_resolve_request_organization` + hand-rolled `_enforce_csrf` (`billing/views.py:62, 81`); listings a fourth variant. Meanwhile no `REST_FRAMEWORK` settings exist anywhere in the repo or templates (verified by grep), so DRF's global default is `AllowAny` — module APIs are gated by whatever each module's shim happens to do, not by a declared permission baseline.
- **Why it compounds:** Every new module surface (teams is next) must re-derive the two-obligation contract; each divergent shim is a place where the next change breaks one module's semantics but not another's; and the superuser test posture guarantees the whole class stays invisible until production. The D2 System-org concept will be load-bearing for every public surface the SaaS direction adds.
- **Correct shape:** One orgs-owned request-context seam that resolves identity + org + GUC in a single call for all module surfaces — anonymous public reads go through one helper that both scopes the queryset and primes the tenant context (the social idiom, generalized) — plus a generated DRF baseline (`DEFAULT_PERMISSION_CLASSES = IsAuthenticated`) so public endpoints are an explicit opt-in, not a default.
- **Trigger for urgency:** The first hardened saas-mode deployment with public content (the beta-site migration is in planning — `docs/planning/beta-site-migration.md`), or the teams module shipping new public/anonymous surfaces on the same broken pattern.
- **Compounding factor:** blog public list/detail/category/tag views, listings list/detail, blog staff API writes (System-org fallback), crm's per-request seeding write, billing's bespoke shims — all built on the absent seam.
- **Detection signal:** Today: none in CI (superuser masks it). In production: public blog/listings pages rendering empty while admin shows published System-org rows; also blog API writes failing `WITH CHECK` under the restricted role. Instrument: an E2E smoke that runs the generated app under `RUNTIME_DATABASE_URL` and asserts anonymous `/blog/` shows a published System-org post — this single test covers the whole class.
- **Strongest counter-argument (steelman):** RLS is doing exactly its job — fail-closed, no data leaked — and one could call empty public pages a safe degradation. But the D2 contract says anonymous visitors *must* see System-org rows; a public marketing/blog surface that silently shows nothing in production is a product failure discovered by the customer, and "safe" here means the defect ships. No condition makes this acceptable to keep.
- **Alternative solutions:**
  1. **Shared context helper + DRF baseline (orgs-owned):** add `public_system_org_context()` / an `OrgScopedView`/`PublicSystemOrgReadMixin` pair to orgs that filter *and* prime; migrate blog/listings to it; emit `REST_FRAMEWORK` defaults (IsAuthenticated) from the settings wiring. Effort: low-medium; fixes the defect and the root; per-module migration is mechanical.
  2. **Middleware-level public-context resolution:** TenantMiddleware sets System-org context for anonymous requests on declared public route prefixes (declared in each module's manifest). Effort: medium; centralizes the decision but adds a route-registry to maintain (and middleware already carries one hand-maintained path classifier, `middleware.py:225–263`).
  3. **RLS policy carve-out for published System-org rows:** a second policy `USING (organization_id = <system-org> AND published)` pushes D2 into the database. Effort: medium-high; strongest guarantee, but embeds a data-dependent org id and per-table publish semantics into policy DDL — brittle across modules with different "published" notions.
- **Preferred option + why:** (1). It generalizes the idiom social already proved, keeps D2 semantics in one owned seam, gives module APIs a real permission baseline, and is the smallest change that both fixes blog/listings now and removes the per-module reinvention. Pair it with the restricted-role E2E smoke regardless of option.
- **Migration path:** Add the orgs-owned public-read helper (filter + `tenant_context(system_org)`), convert `blog/views.py` `_scope_by_org` to it, and land the restricted-role anonymous `/blog/` E2E in the same PR.
